# Лаунчер: раздача модпака и запуск клиента

**Дата:** 2026-09-03
**Статус:** черновик; вход в игру решён владельцем 2026-09-03 (offline-mode)
**Место в дорожной карте:** подсистема 6
**Связано:** `mods/MODLIST.md` — источник истины по составу пака

## 1. Что делает подсистема

Восьми игрокам нужно оказаться в одинаковом клиенте: Minecraft 1.21.1,
NeoForge 21.1.249, 86 сторонних модов плюс `plaguecore`, одинаковые
конфиги, одинаковые ресурспаки. Собирать это руками восемь раз — верный
способ провести первый вечер сессии за разбором чужих крашлогов.

Лаунчер решает ровно одну задачу: **привести папку игрока в состояние,
описанное манифестом, и запустить игру.** Он не менеджер модпаков, не
магазин и не чат. Один пак, одна кнопка.

Второе требование — **подгрузка файлов по ходу сессии.** Сессия идёт
четыре дня, и за это время почти наверняка придётся выкатить правку
баланса, новый ресурспак под сюжетный поворот или чиненый `plaguecore`.
Без лаунчера это восемь личных сообщений «скачай, положи сюда, перезапусти».

Границы: лаунчер ничего не знает про чуму. Он оперирует файлами, хешами
и версиями. Игровая логика — не здесь.

## 2. Что уже есть и чего нет

Есть: `mods/MODLIST.md` с точными именами джарников, собираемый
`plaguecore-0.1.0.jar`, приватный репозиторий на GitHub.

Нет ничего из следующего:

- самих джарников в репозитории — они намеренно в `.gitignore`,
  и это правильно, но значит раздавать их надо иначе
- конфигов, ресурспаков и KubeJS-скриптов как отдельного набора файлов;
  сейчас они существуют только в чьей-то локальной папке
- сервера — хостинг под сессию ещё не выбран, адрес в манифесте пока
  заглушка

## 3. Технология

**Electron.** Выбран владельцем из пары Electron/Tauri, окончательный
выбор сделан в пользу Electron: Tauri требует Rust, то есть третьего
языка в проекте после Java и JavaScript. Инсталлятор выйдет около 150 МБ
против 10 у Tauri, но игрок в любом случае качает больше гигабайта
модов и ассетов — на этом фоне разница не имеет значения.

Что осознанно не выбрано:

| Вариант | Почему нет |
|---|---|
| Prism Launcher + готовый пак | Ноль кода, но обновления только руками, а подгрузка файлов по ходу сессии невозможна в принципе |
| Свой лаунчер на Java | Один стек с модом, но GUI на Swing/JavaFX в 2026 году — отдельный источник боли |
| CurseForge/Modrinth App | Требует публикации пака на чужой площадке; пак приватный и таким останется |

Вся тяжёлая работа лаунчера — скачивание, подсчёт хешей, распаковка,
запуск процесса — в Node.js делается штатными средствами.

## 4. Манифест

Единственный источник истины о том, как должен выглядеть клиент. Лежит
в релизе на GitHub, версионируется целым числом.

```json
{
  "packVersion": 12,
  "minecraft": "1.21.1",
  "neoforge": "21.1.249",
  "java": { "major": 21 },
  "launch": {
    "maxRamMb": 6144,
    "jvmArgs": ["-XX:+UseG1GC", "-XX:MaxGCPauseMillis=50"]
  },
  "server": { "host": "plague.example.net", "port": 25565 },
  "managedDirs": ["mods", "config", "defaultconfigs", "kubejs", "resourcepacks", "shaderpacks"],
  "files": [
    {
      "path": "mods/create-1.21.1-6.0.10.jar",
      "sha256": "a3f1…",
      "size": 18234567,
      "url": "https://github.com/…/releases/download/pack-12/create-1.21.1-6.0.10.jar"
    }
  ]
}
```

`packVersion` растёт при любом изменении содержимого. Лаунчер сравнивает
его с локально сохранённым и по этому числу понимает, нужна ли сверка
вообще — это дешёвая проверка одного HTTP-запроса вместо пересчёта хешей
тысячи файлов.

Манифест собирается скриптом из реальной папки: скрипт обходит
`managedDirs`, считает SHA-256, пишет JSON. Руками его не редактируют —
иначе он рано или поздно разойдётся с действительностью.

## 5. Управляемые и пользовательские файлы

Ключевое разделение, из которого растёт «запрет сторонних модов».

**Управляемые папки** (`managedDirs`) синхронизируются жёстко:

- файла нет или хеш не совпал → скачать
- файл есть, а в манифесте его нет → **удалить**

Именно второе правило и запрещает посторонние моды. Игрок может положить
в `mods/` что угодно, но следующий запуск это вычистит.

**Пользовательские файлы** лаунчер не трогает никогда: `options.txt`,
`saves/`, `screenshots/`, `logs/`, `servers.dat`, настройки шейдеров и
раскладка клавиш. Иначе на третий день сессии кто-нибудь потеряет свои
настройки управления и будет прав в своём возмущении.

**Честное ограничение.** Удаление на стороне лаунчера — не защита, а
гигиена. Игрок, запустивший игру мимо лаунчера, обойдёт её за минуту.
Настоящая проверка состава модов возможна только на сервере, при
подключении. Это территория подсистемы игровой логики — вынести в
отдельную задачу и согласовать со вторым разработчиком.

## 6. Отдельная папка инстанса

Лаунчер работает в своей папке, а не в общем `.minecraft`:

```
%APPDATA%\PlagueLauncher\
  instance\        ← игровая папка: mods, config, saves, options.txt
  runtime\         ← своя JRE 21
  versions\        ← Minecraft и NeoForge
  libraries\
  assets\
  launcher.json    ← packVersion, путь, выделенная память, данные входа
```

Причина: у игроков уже есть ванильный Minecraft со своими мирами и
модами. Синхронизация с удалением файлов в общей папке — это гарантия,
что кто-нибудь лишится сборки, которую собирал полгода.

## 7. Java у игрока

Лаунчер **не полагается на системную Java.** Опыт этого проекта: на
машине владельца стоят четыре разные версии Java, и команда `java`
отвечает той, что не подходит.

При первом запуске лаунчер скачивает Temurin JRE 21 через Adoptium API
(`api.adoptium.net/v3/binary/latest/21/ga/windows/x64/jre/hotspot`),
распаковывает в `runtime\` и дальше пользуется только ей. Около 45 МБ,
один раз.

## 8. Установка Minecraft и NeoForge

Порядок, в котором лаунчер приводит клиент в рабочее состояние:

1. **Ванильный клиент.** `version_manifest_v2.json` от Mojang → запись
   про 1.21.1 → `client.jar`, список библиотек, индекс ассетов.
2. **Ассеты.** Около 600 МБ мелкими файлами. Качаются параллельно,
   пачками по 16, с повторами при обрыве. Самый долгий шаг, требует
   внятного прогресс-бара.
3. **NeoForge.** Скачивается официальный installer и запускается нашей
   же JRE в режиме `--install-client`. Он сам разложит библиотеки и
   сгенерирует профиль версии. Свой разбор формата NeoForge писать не
   будем: формат меняется от версии к версии, а установщик поддерживают
   его авторы.
4. **Файлы пака.** Синхронизация по манифесту (раздел 5).

Шаги 1–3 выполняются один раз и кэшируются. Шаг 4 — при каждом запуске.

## 9. Запуск

Из профиля версии, который оставил установщик NeoForge, собирается
classpath и аргументы. Java-процесс запускается с рабочей папкой
`instance\`. Логи пишутся в файл и показываются в окне лаунчера — иначе
разбор чужого краша превратится в переписку «пришли скриншот».

Опционально: `--server` и `--port` из манифеста, чтобы игра сразу
подключалась к нашему серверу, минуя список серверов.

## 10. Подгрузка файлов по ходу сессии

Требование владельца, разбирается честно, потому что здесь есть предел.

**Что работает.** Лаунчер остаётся открытым, пока идёт игра, и раз в
пять минут проверяет `packVersion`. Как только тот вырос, игрок видит
уведомление: «Есть обновление. Перезайдите, когда будет удобно». Файлы
докачиваются в фоне, применяются при следующем запуске. От выкладки
правки до её появления у всех — минуты, а не вечер переписки.

**Чего не будет и не может быть.** Minecraft не умеет подхватывать моды
на лету. Ни один лаунчер этого не умеет, включая коммерческие. Замена
джарника требует перезапуска игры — это ограничение платформы, а не
нашей реализации.

**Обходной путь для косметики.** Ресурспак сервер умеет раздавать сам,
штатным механизмом `resource-pack` в `server.properties`: игрок получает
его при подключении, без всякого лаунчера. Если по сюжету надо на третью
ночь поменять всем текстуры или музыку — это делается так, и лаунчер тут
не нужен. Стоит заложить в дизайн сюжетных поворотов.

## 11. Вход в игру

**Решение владельца от 2026-09-03: сервер работает в `offline-mode`.**
Играют восемь друзей, доверие между ними есть, проверка личности
Microsoft не нужна.

Что это означает для лаунчера. Игрок при первом запуске вводит ник,
лаунчер сохраняет его в `launcher.json` и передаёт игре. UUID считается
локально, тем же способом, что и у сервера в offline-режиме: MD5 от
строки `OfflinePlayer:<ник>`, версия 3. Совпадение алгоритма
обязательно — иначе игрок при каждом входе будет получать новый UUID и
терять инвентарь, дом и прогресс класса.

Модуль входа остаётся отдельным: если позже понадобится Microsoft,
меняется он один, остальные разделы не затрагиваются.

Что при этом надо закрыть на стороне сервера, вне лаунчера:

- **белый список ников** (`white-list=true`) — иначе адрес сервера,
  случайно попавший наружу, пускает кого угодно
- **`online-mode=false`** и понимание, что права оператора теперь
  держатся на нике, а не на аккаунте: administrator-ник займёт любой,
  кто его наберёт. Оператора выдавать по белому списку, а не раздавать
  свободно.

Скины в offline-режиме не подгружаются автоматически. Если это важно
для атмосферы — решается модом на скины или своим сервером скинов,
вопрос отдельный и на лаунчер не влияет.

## 12. Раздача файлов и чужие лицензии

Выбран GitHub Releases. Два уточнения, которые лучше проговорить сейчас.

**Репозиторий должен остаться приватным.** 86 модов — чужая работа, и
лицензии у них разные; часть распространять запрещено. Выкладывание их в
публичный релиз — это перераспространение чужого софта. В приватном
релизе для восьми друзей — это личная копия пака, ситуация та же, что и
передача архива по почте.

**Приватный релиз требует токена.** Лаунчер получает файлы с токеном
доступа только на чтение. Токен окажется внутри сборки лаунчера, то есть
извлекаем любым, кто откроет установщик, — против случайного человека
защищает, против настойчивого нет. Для круга из восьми человек этого
достаточно; ротация токена = пересборка лаунчера.

Альтернатива на будущее, если круг расширится: раздача с того же
сервера, где Minecraft, по HTTP с паролем.

## 13. Чего не будет в первой версии

- автообновления самого лаунчера — обновлять будем присылкой нового
  установщика, восемь человек это переживут
- нескольких профилей и модпаков
- красивого интерфейса: одно окно, кнопка, прогресс-бар, лог
- Linux и macOS — сборка только под Windows, если у кого-то иначе,
  вопрос решается отдельно
- статистики, достижений, новостной ленты

## 14. Порядок реализации

Каждый пункт проверяем и осмысленен сам по себе.

1. Каркас Electron: окно, сборка установщика под Windows
2. Модель манифеста и его разбор, с тестами на битые данные
3. Скрипт сборки манифеста из папки пака
4. Загрузчик файлов: параллельность, повторы, проверка SHA-256, прогресс
5. Синхронизация папки по манифесту, включая удаление лишнего
6. Установка JRE 21 из Adoptium
7. Установка ванильного клиента и ассетов
8. Установка NeoForge через официальный installer
9. Сборка команды запуска и запуск, вывод логов в окно
10. Авторизация — после решения по разделу 11
11. Проверка обновлений во время игры и уведомление
12. Первая раздача: релиз пака, сборка установщика, проверка на второй
    машине

Пункты 1–9 не зависят от решения по авторизации и делаются сразу.
