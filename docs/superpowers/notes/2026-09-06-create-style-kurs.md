# Курс проекта: create-style во всём

**Дата:** 2026-09-06
**Статус:** действующее правило, отменяет прежнее «мост к Create только мягкий»
**Кто решил:** владелец, прямым указанием в сессии

## Правило

Дословная формулировка владельца: «отталкиваться только от create
моделек и текстурок, переходим на create-style, и зависимость от мода
create — подтягивать все механики оттуда».

Правило состоит из трёх частей, и все три постоянные.

### 1. Внешний вид отталкивается от Create

Делая модель или текстуру, исходником берутся настоящие ассеты Create,
а не рисунок с нуля:

```
create:block/andesite_casing         оправа андезитового тира
create:block/brass_casing            оправа латунного тира
create:block/andesite_casing_short   узкие пояски, воротники
create:block/axis_top                торец вала — гнёзда и порты
```

Достаются обычным `unzip` из `mods/create-1.21.1-6.0.10.jar`.
Обрабатывать их можно и нужно — обесцвечивать, тонировать, вырубать
отверстия; так сделаны `andesite_purifier_casing.png` (обесцвеченный
`andesite_casing`) и `andesite_purifier_socket.png` (он же с вырубленным
отверстием и вложенным торцом вала).

Ссылаться на текстуру Create прямо из модели —
`"casing": "create:block/andesite_casing"` — нормальный приём, копию
в свои ассеты класть не обязательно.

**Уточнение владельца от того же дня: готовое лучше производного.**
Дословно — «мы должны при возможности пользоваться уже существующими
текстурами из Create, в том числе и латунь». То есть сначала ищется
готовая текстура Create, делающая нужное, и только если такой нет,
делается производная. Повод: голове латунного очистителя была сделана
производная от `brass_casing`, тогда как у Create уже есть
`brass_block` — настоящая полированная латунь, ровно тот светлый металл
на тёмном корпусе, который и требовался. Производная у латунного тира
осталась ровно одна — гнездо вала, которого у Create нет и быть не
может. Разбор — `2026-09-06-latunnyj-ochistitel-oblik.md`.

Повод для правила: самодельная `andesite_purifier_side.png` из
`textures_src/create_sprayer/` была признана владельцем «менее
канонично и стилистически create-овски» выглядящей.

### 2. Зависимость на Create жёсткая

**Отменяется** прежнее решение, записанное в `lmpc_classes/CLAUDE.md`
и в javadoc `CreateBridge`: «наследоваться от `KineticBlockEntity`
значило бы завести жёсткую зависимость, без Create мод перестал бы
грузиться целиком».

Теперь так и делается. Блоки наследуются от классов Create напрямую,
`create` помечается `required` в `neoforge.mods.toml`, и без Create
мод не грузится.

Решение защитимо и принято с открытыми глазами:

- Create в этом паке есть всегда — на нём держится весь замысел сессии;
- мод уже жёстко требует Curios, так что вторая обязательная
  зависимость природу сборки не меняет;
- взамен получаем настоящий вал, вращение, стресс и рендер
  крутящихся деталей даром, вместо самописных подобий.

### 3. Механики берутся у Create, а не переписываются

Если Create уже умеет нужное — вращение, стресс (SU), вал, сборочная
линия, рендер вращающихся деталей, — используется его реализация,
а не своя на ванильных хуках. Блок должен **быть** машиной Create,
а не быть на неё похожим.

Первое следствие: `ponytail:` в `CreateBridge` про непотреблённый
стресс закрывается сам собой — `calculateStressApplied` у настоящего
`KineticBlockEntity` работает, и «64 SU на штуку» из спека ядра 10.1
наконец начинает что-то значить.

## Чего правило НЕ касается

Мост к `plaguecore` (`PlagueBridge` отсюда, `ClassesApi` туда)
**остаётся мягким и рефлексивным**. Причина там другая: два наших мода
развиваются порознь, в разных сессиях и двумя людьми, и жёсткая связь
между ними ломала бы сборку у того, чья половина отстала. Это правило
про Create, не про наши моды между собой.

Своя графика по-прежнему уместна там, где Create ни при чём: алтарь
призвания, грядка бутона чумы, предметы Клирика и Летописца.

## Что из этого уже сделано

- `andesite_purifier` переведён на текстуры от Create — заметка
  `2026-09-06-ochistitel-create-style.md`;
- `build.gradle` тянет Create, Flywheel и Registrate на компиляцию;
- наследование очистителя от `KineticBlockEntity` — **в работе**,
  не закончено.

## Что по этому правилу предстоит

- Довести очиститель до настоящего кинетического блока: `KineticBlock`,
  `KineticBlockEntity`, стресс, рендер полувала (`AllPartialModels.SHAFT_HALF`)
  в нижнем порту.
- Латунный очиститель тем же путём: `brass_casing` в основе, своё гнездо.
- `CreateBridge` после этого становится не нужен — его работу делает
  сам `KineticBlockEntity`.
- Пересмотреть сцены Ponder: у настоящего кинетического блока вал
  цепляется по правилам Create, и костыль с записью `Speed` в NBT
  может стать лишним.
