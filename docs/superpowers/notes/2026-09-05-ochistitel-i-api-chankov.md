**Затрагивает чужую папку:** да — `plaguecore/mc/PlagueApi.java`, только

## Зачем понадобилось лезть в `plaguecore`

`PlagueApi` до сих пор отдавал наружу только состояние **игрока**:
`cure`, `grantImmunity`, `getStage`, `getInfection`, `getPermanentLoss`.
Три из четырёх классов упираются не в игрока, а в **местность**:

- грядка Фермера должна знать, заражён ли чанк, чтобы дикий бутон
  падал в Гнили, а не на грядке у дома;
- Очиститель Кузнеца обязан снижать уровень чанка и поднимать его
  сопротивление — это его единственная работа;
- снимок Летописца показывает уровни чанков в радиусе.

Единственная альтернатива — рефлексия на `PlagueState`/`PlagueGrid`
в обход интерфейса. Это хуже: `PlagueApi` для того и заведён, чтобы
классы не зависели от внутренностей ядра, а обход означал бы, что
любая перестановка полей в `PlagueGrid` молча ломает три класса.

## Что добавлено (ничего не изменено и не удалено)

```java
int     PlagueApi.getChunkLevel(ServerLevel, int чанкX, int чанкZ)   // 0..5, -1 вне сетки
int     PlagueApi.getChunkLevelAt(ServerLevel, BlockPos)
float   PlagueApi.getChunkResistance(ServerLevel, int чанкX, int чанкZ)
int     PlagueApi.getNight(ServerLevel)
boolean PlagueApi.cleanseChunk(ServerLevel, int чанкX, int чанкZ,
                               float сила, float приростСопротивления)
void    PlagueApi.recordSnapshot(ServerPlayer, BlockPos)
```

Существующие методы не тронуты, поведение чумы не изменилось.

**`cleanseChunk` — это ночной шаг очистителя из спека ядра, раздел
10.1**, и правило 10.2 («нельзя окопаться») живёт **внутри него**,
а не в блоке очистителя. Так сделано намеренно: правило про баланс
эпидемии, и любой будущий очиститель — латунный, электрический, чей
угодно — обязан ему подчиняться, не переписывая условие у себя.
Если правило понадобится поменять, менять его надо здесь, в одном
месте.

**`recordSnapshot` — пустой крючок под подсистему 5 «Лор»**, ровно
как обещал спек классов (раздел 7). Сейчас пишет строку в debug-лог.
Разведывательный эффект снимка целиком живёт в `lmpc_classes`
и от этого крючка не зависит — наполнять его можно спокойно и потом.

## Как это видно со стороны классов

`lmpc_classes` по-прежнему **не имеет Gradle-зависимости** на
`plaguecore` и ходит через рефлексию (`PlagueBridge`). Новые методы
там объявлены **необязательными**: если их не окажется (старая версия
соседа), отвалится ровно одна способность, а не весь мод и не отвар
Клирика. Проверять наличие `plaguecore` по-прежнему через
`PlagueBridge.доступен()`.

## Что от этого может понадобиться владельцу `plaguecore`

Ничего обязательного. Но если ядро когда-нибудь начнёт считать
очистители само (сейчас их считает `lmpc_classes`), `cleanseChunk`
уже готовая точка для этого — переносить правило 10.2 не придётся.
