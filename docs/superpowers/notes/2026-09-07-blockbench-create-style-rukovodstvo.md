# Blockbench и create-style: рабочее руководство для следующих сессий

**Дата:** 2026-09-07
**Затрагивает чужую папку:** нет. Правки в `docs/`, `textures_src/`
и комментариях `lmpc_classes/`.

Это сводный документ: где лежат инструменты, как гонять Blockbench
через MCP и — главное — какие числа и приёмы Create считать
каноническими. Он написан потому, что предыдущая сессия несколько раз
переоткрывала одно и то же и один раз записала в заметку неверную
цифру, которая потом разошлась по трём файлам. Читать его до того, как
открывать Blockbench.

## Как гонять Blockbench через MCP

Работа идёт через `risky_eval` — владелец разрешил пользоваться им без
спроса. Отдельные MCP-инструменты (`place_cube` и прочие) годятся для
одного куба; всё, что сложнее, пишется генератором.

**Порядок создания куба строгий:**

```js
new Cube({name, from, to, faces}).addTo(group).init();
```

`.init()` в конце обязателен, иначе куб не появится в сцене.

**Ловушка с глобальными переменными.** Каждый `risky_eval` выполняется
в области видимости бандла Blockbench, где полно однобуквенных
локальных имён. `globalThis.T = ...`, а потом обращение к голому `T`
в следующем вызове разрешится в чужую локальную `T` — получите
`TypeError: Cannot read properties of undefined (reading 'uuid')`.
Два правила:

1. Имя глобали — редкое и заметное (`globalThis.PUR`, не `T`, не `PF`).
2. Обращаться всегда полным путём: `globalThis.PUR.mk(...)`.

Кроме того, объект глобали между вызовами **теряет часть ключей** —
наблюдалось, что переживают только добавленные позже. Поэтому весь
каркас определяется одним `risky_eval` целиком, а не дописывается по
кусочкам.

**Рабочий каркас** (переопределяется целиком при каждом изменении):

```js
globalThis.PUR = {
  DIR: 'E:\\BLOCKBENCHCLAUDE\\work\\purifier\\',
  tex(file) {            // переиспользует текстуру по имени
    const n = file.replace('.png','');
    return Texture.all.find(t => t.name === n)
        || new Texture({name: n}).fromPath(this.DIR + file).add();
  },
  clear() { Cube.all.slice().forEach(c => c.remove()); },
  mk(spec) { return new Cube(spec).addTo(Group.selected || undefined).init(); },
  build(list) { this.clear(); return list.map(s => this.mk(s)).length; },
  shot(file, cb) {       // скриншот превью на диск
    Preview.selected.screenshot({}, url => {
      require('fs').writeFileSync(this.DIR + file,
        Buffer.from(url.split(',')[1], 'base64'));
      cb && cb();
    });
  }
};
```

**Скриншот после каждого шага** — это из `MODEL_GENERATION_GUIDE.md`
и это не формальность: белые щели, просвечивающие грани и слипшиеся
ярусы видно только глазом. Снимать и сверху, и **снизу** — нижняя
грань у машин Create самая нагруженная.

## Канон Create: числа

### Вал — 4×4, а не 6×6

Это та самая цифра, которую предыдущая сессия записала неверно.
Проверено дважды, двумя независимыми способами:

- `src_assets/create/models/block/shaft.json`: единственный элемент
  `from [6,0,6] → to [10,16,10]`. Это **4 пикселя** по X и Z.
- `textures/block/axis_top.png`: непрозрачные пиксели занимают ровно
  квадрат x 6..9, y 6..9 — снова 4 пикселя.

```bash
# как перемерить, если не верится
python -c "
from PIL import Image
im=Image.open('src_assets/create/textures/block/axis_top.png').convert('RGBA'); px=im.load()
xs=[x for y in range(16) for x in range(16) if px[x,y][3]>0]
print(min(xs), max(xs))"   # -> 6 9
```

**Следствие:** гнездо под вал в наших моделях должно быть рассчитано
на 4×4, а не на 6×6. Наша `andesite_purifier_socket.png` имеет чёрное
отверстие 8×8 (измерено: тёмные пиксели x 4..11) — вдвое шире канона.

### Гнездо вала — готовая текстура `create:block/gearbox`

Своё гнездо рисовать не надо: у Create оно уже есть и используется
везде, где вал входит в машину снизу. `textures/block/gearbox.png` —
это `andesite_casing` с круглым тёмным отверстием посередине:

```
 5 ......+##+......
 6 .....+####+.....
 7 .....######.....
 8 .....######.....
 9 .....+####+.....
10 ......+##+......
```

Сплошное ядро — x 6..9 (те же 4 пикселя, что торец вала), вокруг —
скруглённое затенение до 5..10. То есть текстура нарисована ровно под
вал 4×4 и уже содержит фаску. Это прямое попадание в правило проекта
«готовая текстура Create предпочтительнее своей производной»
(`create-style-kurs-proekta`).

### Гнездо вала — структурная идиома

Эталон — `src_assets/create/models/block/encased_cogwheel/block_bottom.json`.
Схема такая:

```
корпус  [0,1,0] → [16,6,16]   down: create:block/gearbox, uv [0,0,16,16]
юбка N  [0,0,0] → [16,1,2]  ┐
юбка S  [0,0,14]→ [16,1,16] │  четыре полоски andesite_casing высотой
юбка W  [0,0,2] → [2,1,14]  │  в 1 пиксель по краю нижней грани
юбка E  [14,0,2]→ [16,1,14] ┘
```

Корпус поднят на 1 пиксель, гнездо утоплено в эту нишу, а по периметру
идёт рамка оправы в один пиксель. Получается, что отверстие лежит
в углублении, а не наклеено на плоское дно.

**Геометрии вала в модели блока нет и быть не должно.** Ни в одной
модели Create вал не является частью машины: торчащий огрызок рисует
рендерер (`KineticBlockEntityRenderer.shaft(axis)`), а модель даёт
только гнездо. У нас это ровно так же — `PurifierRenderer` берёт
настоящую модель вала Create, поэтому геометрия у него верная, неверны
были только комментарии про 6×6.

### Ярусы и z-fighting

Машины Create собраны из плит, а не из одной коробки: низ — оправа,
середина — утопленное ядро, верх — оправа. `gearbox/block.json`:

```
Bottom [0,0,0]      → [16,2,16]        andesite_casing
Core   [0.95,2,0.95]→ [15.05,14,15.05] gearbox, uv [1,2,15,14]
Top    [0,14,0]     → [16,16,16]       andesite_casing
```

Обратите внимание на `0.95`/`15.05`: ядро сделано **чуть шире** ниши
намеренно — так грани не совпадают ровно и не мерцают. Приём копировать
можно и нужно.

### Прозрачность внутри текстур Create — ловушка UV

Часть текстур Create прозрачна не только по краям. У
`mixer_base_side.png` строки 14 и 15 прозрачны полностью. Если взять
окно UV `[0,10,16,16]`, потому что «хочу нижние 6 пикселей», грань
станет частично сквозной — это и был баг «моделька забагованная снизу,
прозрачная текстура просвечивает».

**Правило: не выдумывать окна UV, а брать те, которыми пользуется сам
Create.** Для `mixer_base_side` это `[0,10,16,14]` для нижнего пояса
и `[0,0,16,6]` для верхнего. Проверить окно можно так:

```bash
python -c "
from PIL import Image
im=Image.open('<текстура>.png').convert('RGBA'); px=im.load()
x1,y1,x2,y2 = 0,10,16,16                       # проверяемое окно
bad=[(x,y) for y in range(y1,y2) for x in range(x1,x2) if px[x,y][3]<255]
print('полупрозрачных пикселей в окне:', len(bad))"
```

## Порядок работы над моделью блока

1. **Найти прототип в `src_assets/create/models/block/`.** Почти всё,
   что нужно, у Create уже нарисовано: корпус машины, гнездо вала,
   решётка, воронка. `grep -l` по текстуре в моделях находит все блоки,
   которые её используют, — это быстрый способ увидеть каноничные окна
   UV для этой текстуры.
2. **Собрать генератором в Blockbench**, не руками. Скриншот после
   каждого шага, включая вид снизу.
3. **Проверить UV на прозрачность** скриптом выше — все грани, не
   только подозрительные.
4. **Развилки нести владельцу вариантами** (`reshenia-predlagat-variantami`):
   силуэт, набор ярусов, какую текстуру взять — это дизайнерские
   решения, а не рутина.
5. **Сохранить `.bbmodel`** в `textures_src/<блок>/`, а `.json`
   в `lmpc_classes/src/main/resources/assets/lmpc_classes/models/block/`.
6. **Записать открытые правки в заметку** (`otkrytye-pravki-v-git`).
