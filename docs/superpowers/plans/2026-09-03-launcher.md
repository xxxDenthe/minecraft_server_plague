# Лаунчер: первая рабочая версия — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Игрок скачивает один установщик, запускает, вводит ник и нажимает «Играть». Через двадцать минут он в нашем мире с правильными 87 модами. На четвёртый день сессии мы выкладываем правку, и она приезжает ко всем без единого сообщения в чат.

**Architecture:** Основной процесс Electron — это Node, и вся работа с файлами, сетью и запуском игры живёт там, разбитая на модули без зависимостей друг от друга. Каждый модуль — чистая функция или класс над файловой системой, тестируется обычным запуском без окна. Окно (renderer) не знает ничего, кроме событий прогресса: оно рисует полоску и лог. Такое разделение нужно, чтобы отлаживать установку Minecraft за секунды в терминале, а не кликая по интерфейсу.

**Tech Stack:** Node 24, Electron, electron-builder, Vitest.

## Global Constraints

- Minecraft **1.21.1**, загрузчик **NeoForge 21.1.249** — те же версии, что в `mods/MODLIST.md`
- Node **24.19**, npm **11.17** (установлены)
- Кэши уведены на диск D: `GRADLE_USER_HOME`, npm cache, `ELECTRON_CACHE` — на системном диске места мало
- Лаунчер живёт в подпапке **`launcher/`** репозитория, рядом с `plaguecore/`
- Целевая платформа первой версии — **только Windows x64**
- Вход — **offline-mode**, без Microsoft. UUID: версия 3 (MD5) от UTF-8 строки `OfflinePlayer:<ник>`
- Игровая папка — **своя**, `%APPDATA%\PlagueLauncher\`, ванильный `.minecraft` не трогается ни при каких обстоятельствах
- Ни один модуль основного процесса не импортирует `electron` — кроме `src/main/index.js`. Это проверяется тестом, по образцу `CorePurityTest` в ядре мода
- Коммиты — на русском, в конце каждого:
  `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`

**Спек:** `docs/superpowers/specs/2026-09-03-launcher-design.md`

**Что этот план НЕ делает** (при необходимости — следующие планы): автообновление самого лаунчера, несколько профилей, Linux и macOS, вход через Microsoft, серверная проверка состава модов (чужая зона, отдельная задача).

```

  vitest.config.js
  src/
    main/

      sync.js           приведение папки к состоянию манифеста
      java.js           установка JRE 21 из Adoptium
      minecraft.js      ванильный клиент, библиотеки, ассеты
      neoforge.js       установка NeoForge официальным установщиком
      launch.js         сборка команды запуска, запуск, чтение логов
      progress.js       единый формат событий прогресса
    preload.js          мост между окном и основным процессом
    renderer/
      index.html
      renderer.js
      style.css
  tools/
    build-manifest.js   сборка манифеста из готовой папки пака
  test/
    manifest.test.js
    offline.test.js
    download.test.js
    sync.test.js
    paths.test.js
```

Разделение по ответственности: каждый файл отвечает на один вопрос. `sync.js` не знает, откуда берутся файлы, — он получает готовый загрузчик. `minecraft.js` не знает про NeoForge. Это позволяет тестировать установку на подставных данных, не выкачивая гигабайты.

**Files:**
- Create: `launcher/src/main/manifest.js`

Проверить, что разбор падает с понятной ошибкой на каждом из случаев:

- не JSON вообще
- нет поля `packVersion` или оно не целое
- `files` не массив
- у файла нет `path`, `sha256` или `url`

### Task 4: UUID оффлайн-игрока

**Files:**
- Create: `launcher/src/main/offline.js`
- Test: `launcher/test/offline.test.js`

**Interfaces:**
- Consumes: ничего
- Produces: `offlineUuid(nickname)` → строка вида `8-4-4-4-12`

- [x] **Step 1: Тест на совпадение с сервером**

Алгоритм: MD5 от UTF-8 байтов строки `OfflinePlayer:<ник>`, затем выставить версию 3 и вариант RFC 4122 — то есть байт 6 получает старшие биты `0011`, байт 8 получает старшие биты `10`.

Контрольные значения взять **из работающего сервера**: поднять ванильный 1.21.1 в offline-режиме, зайти двумя никами, прочитать UUID из `usercache.json`. Придумывать ожидаемые значения из головы нельзя — весь смысл теста в совпадении с чужой реализацией.

Проверить минимум: обычный ник, ник с цифрами, ник в 16 символов, ник с подчёркиванием.

- [x] **Step 2: Реализовать**

Через `node:crypto`, десять строк. Тест либо совпадает с сервером, либо задача не сделана.

**Почему это отдельная задача на десять строк.** Ошибка здесь не видна ни в логах, ни при запуске: игра стартует, игрок заходит, всё работает. И только на второй день выясняется, что у половины людей каждый вход создаёт нового персонажа. Дешевле проверить сейчас.

### Task 5: Загрузчик файлов

**Files:**
- Create: `launcher/src/main/download.js`
- Create: `launcher/src/main/progress.js`
- Test: `launcher/test/download.test.js`

**Interfaces:**
- Consumes: `progress.js`
- Produces: `downloadFile({url, dest, sha256, size, headers})`, `downloadAll(items, {concurrency, onProgress})`, `sha256OfFile(path)`

- [x] **Step 1: Тесты на локальном HTTP-сервере**

Поднять `node:http` на случайном порту прямо в тесте и проверить:

- файл скачивается, хеш совпадает
- при несовпадении хеша файл **удаляется** и бросается ошибка — недокачанный джарник в `mods/` хуже, чем его отсутствие
- обрыв соединения приводит к повтору, три попытки с нарастающей паузой
- уже существующий файл с верным хешем **не скачивается заново**
- скачивание идёт во временный файл и переименовывается только после проверки

Последнее важно: игрок закроет лаунчер на середине, и папка не должна остаться с обрубками.

- [x] **Step 2: Реализовать через `fetch` и потоки**

Хеш считается на лету, во время записи, а не вторым проходом по файлу. На тысяче файлов разница заметна.

- [x] **Step 3: Параллельность и прогресс**

`downloadAll` держит окно из `concurrency` (по умолчанию 8) задач. События прогресса — единого формата из `progress.js`: `{stage, current, total, bytesDone, bytesTotal, message}`.

### Task 6: Синхронизация папки

**Files:**
- Create: `launcher/src/main/sync.js`
- Test: `launcher/test/sync.test.js`

**Interfaces:**
- Consumes: `manifest.js`, `download.js`, `paths.js`
- Produces: `planSync(manifest, instanceDir)` → `{toDownload, toDelete, toKeep}`; `applySync(plan, opts)`

- [x] **Step 1: Тесты на план, без единого скачивания**

`planSync` — чистая функция над состоянием папки, и именно она содержит всю опасную логику. Тесты на временной папке:

- файла нет → в `toDownload`
- файл есть, хеш совпал → в `toKeep`, скачивания нет
- файл есть, хеш не тот → в `toDownload`
- лишний файл в управляемой папке → в `toDelete`
- лишний файл **вне** управляемых папок → не трогается
- `options.txt`, `saves/`, `screenshots/`, `logs/`, `servers.dat` не попадают в `toDelete` **никогда**, даже если лежат внутри управляемой папки
- пустая управляемая папка на диске и непустой манифест → всё в `toDownload`
- **манифест с пустым `files` не приводит к удалению всего** — это признак ошибки загрузки, а не команда стереть пак

Последний пункт — защита от самого дорогого сценария: сервер отдал пустой ответ, лаунчер честно его исполнил, восемь человек остались без модов посреди сессии.

- [x] **Step 2: Реализовать `planSync`**

- [x] **Step 3: Реализовать `applySync`**

Порядок: сначала скачать всё новое, потом удалить лишнее. Не наоборот — если сеть отвалится посередине, лучше остаться с лишними файлами, чем без нужных.
